# План: Архитектура приложения для минификации и оптимизации изображений

Создаём модульное Node.js приложение с двумя точками входа (CLI и экспортируемый API), разделённое на логические слои: обработчик файлов → конфигурация → процессор изображений → оптимизаторы форматов. Sharp как основная библиотека (быстро, активно развивается). Конфигурация через CLI-параметры и JSON-файлы, поддержка рекурсивной обработки папок.

---

## 1. Декомпозиция задачи

**Логические модули:**

1. **CLI Module** — интерфейс для конечных пользователей
   - парсинг аргументов командной строки
   - валидация параметров
   - взывает core API

2. **Core API** — экспортируемое ядро для встраивания в скрипты
   - главная функция обработки
   - интерфейсы и типы
   - оркестрация процессов

3. **Config Module** — управление конфигурацией
   - загрузка JSON-конфигов
   - парсинг CLI-параметров
   - слияние значений по умолчанию

4. **File Handler** — работа с файловой системой
   - поиск файлов (рекурсивная обработка)
   - проверка форматов
   - создание выходных директорий

5. **Processor** — основной обработчик изображений
   - координирует обработку
   - вызывает оптимизаторы нужных форматов
   - логирует прогресс

6. **Format Optimizers** — специализированные обработчики
   - `jpg-optimizer.js` — сжатие JPG
   - `png-optimizer.js` — оптимизация PNG
   - `gif-optimizer.js` — обработка GIF
   - `svg-optimizer.js` — минификация SVG
   - `webp-converter.js` — конвертация в WebP (и JPG/PNG → WebP)
   - `avif-converter.js` — конвертация в AVIF (и JPG/PNG → AVIF)

7. **Utilities** — вспомогательные функции
   - логирование (с уровнями: debug, info, warn, error)
   - расчёт размеров и статистики

      │    │ - конвертацию (WebP)   │
      │    │ - конвертацию (AVIF)   │

      │    └───────┬────────────────┘

**Поток данных:**

1. **Вход** — файлы (диск) + конфигурация (CLI или JSON)
2. **Обработка** — каждый файл проходит через выбранные оптимизаторы
3. **Оптимизация** — сжатие, уменьшение размера, удаление метаданных
4. **Конвертация** — если требуется, создаются WebP/AVIF версии
5. **Вывод** — результаты на диск + логи в консоль

## 3. Архитектура и оркестрация

### Рекомендуемый подход: **Pipeline + Plugin-based (гибрид)**

**Почему?**

- Pipeline обеспечивает чёткий поток данных (файл → оптимизаторы → результат)
- Plugin-based позволяет легко добавлять новые форматы без изменения ядра
- Модульность упрощает тестирование и переиспользование

### Взаимодействие модулей:

```
CLI / API
  ↓
ConfigManager (объединяет CLI-параметры + JSON)
  ↓
FileScanner (находит файлы, фильтрует по расширению)
  ↓
Processor (главный оркестратор)
  ├── 1. Выбирает нужные оптимизаторы для формата
  ├── 2. Запускает основную оптимизацию
  ├── 3. Запускает конвертеры (WebP, AVIF) при необходимости
  ├── 4. Сохраняет результаты
  └── 5. Логирует статистику
  ↓
Logger (stdout)
```

### Оркестрация: параллельная обработка

- **По умолчанию:** обрабатываем файлы **последовательно** (проще, предсказуемо)
- **Опционально:** параллельная обработка (workers/Promise.all) для больших папок
  - Контролируется параметром `--workers N` (по умолчанию 1)

## 4. Агенты (логические роли системы)

### 1. **CLI Agent** (точка входа)

- **Ответственность:** парсинг аргументов, валидация входа, вызов API
- **Взаимодействие:** → ConfigManager → Processor
- **Экспортируемая функция:** `cli(argv)`

### 2. **API Agent** (экспортируемое ядро)

- **Ответственность:** принять конфигурацию, обработать файлы, вернуть результаты
- **Взаимодействие:** ConfigManager → FileScanner → Processor → Logger
- **Экспортируемая функция:** `optimizeImages(options)` → Promise<Result[]>

### 3. **Config Agent**

- **Ответственность:** управление конфигурацией
- **Взаимодействие:** читает JSON-файлы, парсит CLI-параметры, применяет defaults
- **Интерфейс:** `loadConfig(cliArgs, jsonPath?)` → Config object

### 4. **File Scanner Agent**

- **Ответственность:** рекурсивный поиск файлов, фильтрация по расширению
- **Взаимодействие:** принимает папку и фильтры → возвращает массив путей
- **Функция:** `scanFiles(inputDir, extensions, recursive)` → string[]

### 5. **Processor Agent**

- **Ответственность:** оркестрация обработки одного файла или массива
- **Взаимодействие:** выбирает оптимизаторы → запускает их → логирует
- **Функция:** `processFile(inputPath, outputDir, config)` → Result

### 6. **Format Optimizers Agents** (Jpg, Png, Gif, Svg, WebP, AVIF)

- **Ответственность:** специализированная оптимизация конкретного формата
- **Взаимодействие:** получает буфер/путь → возвращает оптимизированный буфер + метаданные
- **Функция:** `optimize(inputBuffer, options)` → {buffer, meta}

### 7. **Logger Agent**

- **Ответственность:** структурированное логирование
- **Взаимодействие:** получает события обработки → выводит в stdout
- **Уровни:** debug, info, warn, error

## 5. Интеграция с опытом gulp-плагина (psimage)

### Что ВЗЯТИ из gulp-подхода:

1. **Идея конвертации в несколько форматов** — psimage позволяет создавать WebP/AVIF из исходников, это хорошая практика
2. **Конфигурация по форматам** — отдельные параметры для каждого формата (quality, effort и т.д.)
3. **Поддержка метаданных** — сохранение/удаление EXIF, цветовых профилей

### Что ПЕРЕРАБОТАТЬ:

1. **Вместо gulp-специфичного** (stream API) → универсальный Node.js API
2. **Вместо плагина** → самостоятельное приложение + экспортируемое ядро
3. **Конфигурация:** gulp требует Gulpfile.js, здесь → JSON + CLI-параметры (более гибко)
4. **Параллелизм:** gulp встроенный, здесь нужно реализовать явно (workers)

### Ограничения gulp-подхода (почему переходим на новое):

- Привязан к gulp, не работает отдельно
- Сложнее использовать в других инструментах (webpack, vite и т.д.)
- Не очень удобно для CLI-утилит
- Меньше контроля над логированием и прогрессом

### Как переиспользуем код:

- Логика оптимизации (sharp-конфиги) → скопировать и адаптировать
- Тесты → переписать для новой архитектуры
- Документация → переиспользовать рекомендации

## 8. Критические моменты архитектуры

### Переиспользуемые паттерны:

- **Config merging pattern** — CLI override JSON override defaults (используется везде)
- **Plugin-based optimizers** — легко добавить новый формат (добавить файл в src/optimizers/)
- **Pipeline processing** — каждый этап модулен и тестируем отдельно

### Критические файлы для модификации:

- `src/processor.js` — сердце системы, тут вся бизнес-логика
- `src/optimizers/*.js` — сюда добавляются новые форматы
- `src/config/defaults.js` — все параметры оптимизации

### Критические интерфейсы:

- `optimizeImages(options)` — главный экспорт API
- `processFile(inputPath, outputDir, config)` — обработка одного файла
- каждый оптимизатор: `{optimize(buffer, config)}` — единый интерфейс

## 10. Дополнительные рассмотрения

### A. Параллельная обработка

- **Текущий план:** последовательная (Фаза 1-11), добавляется флаг `--workers N` в Фазе 10
- **Реализация:** Promise.all() для обработки N файлов одновременно
- **Почему позже:** сложнее отлаживать, нужна хорошая архитектура сначала

### B. Кэширование

- **Идея:** если файл не изменился → пропустить обработку
- **Статус:** опционально (Фаза 13+), нужен MD5 или mtime tracking

### 2. JSON-конфиг структура

**Файл: `imgmin-config.json` (или `.imgminrc.json`)**

```json
{
  "formats": {
    "jpg": {
      "quality": 80,
      "progressive": true,
      "removeMetadata": true
    },
    "png": {
      "quality": 9,
      "removeMetadata": true
    },
    "gif": {
      "optimizationLevel": 3,
      "removeMetadata": true
    },
    "svg": {
      "minify": true
    }
  },
  "convertTo": {
    "webp": {
      "enabled": false,
      "quality": 80
    },
    "avif": {
      "enabled": false,
      "quality": 60
    }
  },
  "output": {
    "preserveStructure": true,
    "suffix": ""
  }
}
```

**Ключевые поля:**

- `formats[format].quality` — уровень оптимизации (0-100 для JPG/WebP, 1-11 для PNG)
- `formats[format].removeMetadata` — удалить EXIF и метаданные
- `convertTo[format].enabled` — создавать ли WebP/AVIF версии
- `output.suffix` — суффикс или перезаписывать исходный

### 3. CLI параметры (yargs) — важные:

```bash
# Пример использования:
imgmin --input ./images --output ./dist --quality 75 --remove-metadata --convert-webp

# Полный список флагов:
--input, -i           (required) входная папка
--output, -o          (required) выходная папка
--config, -c          (optional) путь к JSON-конфигу
--quality, -q         (optional) качество для всех форматов (override конфига)
--remove-metadata     (optional) флаг удалить метаданные
--convert-webp        (optional) создать WebP версии
--convert-avif        (optional) создать AVIF версии
--workers             (optional) параллелизм (Фаза 10+, по умолчанию 1)
--verbose             (optional) подробные логи
```

**CLI override JSON override defaults** — иерархия приоритета

### 4. Resize/Scale

✅ **Исключено из scope** — только оптимизация
